RivalLens D2C — Technical Requirements

Implementation blueprint for the D2C competitive-intelligence platform defined in the PRD. This document is written from a production engineering perspective: ship an MVP fast, keep connectors replaceable, preserve evidence provenance, and make the codebase safe to evolve with Claude, Codex, and Cursor.

Architecture: TypeScript-first Data: PostgreSQL + immutable evidence AI: Structured interpretation, never source of truth Build style: Agent-assisted, test-gated
Primary architectureModular monorepo
MVP connectorsWeb · Instagram · X · Meta Ads
Core outputEvidence-backed action report
Key constraintExternal platform instability

1. Engineering Principles

Evidence before inference

Persist source facts first. Derived metrics, signals, and AI explanations must remain downstream and traceable.

Replaceable connectors

Meta, Instagram, X, and crawler integrations must sit behind stable interfaces so provider changes do not infect core logic.

One language for MVP

Use TypeScript across UI, API, workers, connectors, schemas, and jobs. Add Python only when a concrete modeling need justifies it.

Thin AI layer

AI classifies, clusters, summarizes, and explains structured inputs. It must not invent performance metrics or unsupported causal claims.

Observable by default

Every background task must be traceable by run ID, source, status, cost, duration, and error reason.

Vibe-code safely

AI agents can accelerate implementation, but architectural boundaries, schemas, tests, and migrations are human-owned contracts.

6. Connector Requirements

export interface RivalConnector {
  discover(input: DiscoverInput): Promise<DiscoveredSource[]>;
  collect(source: Source): Promise<RawSnapshot>;
  normalize(snapshot: RawSnapshot): Promise<Observation[]>;
  healthCheck(): Promise<ConnectorHealth>;
}
  • Discover homepage, product, pricing, collection, policy, reviews, and promotional pages.
  • Prefer HTTP/HTML extraction where sufficient; escalate to Playwright only when rendering is required.
  • Strip scripts, navigation noise, tracking IDs, timestamps, and unstable markup before hashing.
  • Capture clean text, relevant structured data, screenshot reference, and normalized commerce fields.
  • Respect access restrictions, robots guidance where applicable, rate limits, and platform terms.
  • Support public professional-account data available through compliant API access.
  • Normalize posts, Reels, captions, media type, timestamps, public engagement, and views when returned.
  • Never fabricate private metrics such as saves, reach, CTR, or conversions for competitors.
  • Connector must fail gracefully when the account or metric is unsupported.
  • Collect public post text, timestamps, media, replies, reposts, quotes, likes, and available public metrics.
  • Persist time-series metrics so performance velocity can be computed.
  • Enforce API budget and per-brand collection limits.
  • Must remain provider-neutral because commercial ad access is the least stable integration.
  • Support manual/ad-library import and provider-based ingestion behind the same normalized schema.
  • Store creative type, primary text, headline, CTA, landing page, observed start date, and media reference.
  • Do not infer ROAS, spend, conversions, or targeting when not explicitly available.

10. Security & Compliance

  • Use row-level authorization for organization-scoped data.
  • Keep provider tokens server-side and encrypt sensitive credentials at rest.
  • Never store secrets inside prompts, browser logs, screenshots, or client bundles.
  • Validate and normalize all user-submitted URLs before crawling to reduce SSRF risk.
  • Block private/internal network ranges from crawler targets.
  • Rate-limit onboarding, refresh, export, and report-generation endpoints.
  • Persist only data permitted by the relevant provider/platform contract.
  • Provide deletion paths for user organization data, stored media, and integrations.

11. Observability & Cost Controls

Structured logs

job_id, organization_id, source_id, connector, duration, status, error_code.

Connector health

Success rate, provider latency, authentication state, quota/rate-limit state.

AI costs

Prompt version, model, tokens, media count, latency, estimated cost per analysis/report.

Crawl costs

Browser minutes, fallback-provider calls, pages crawled, bytes stored, screenshot count.

  • Set monthly per-organization budget ceilings for expensive connectors and AI analysis.
  • Skip AI calls if deterministic hashes show no meaningful content changes.
  • Deduplicate identical creatives/posts before multimodal analysis.

14. Claude / Codex / Cursor Development Workflow

Use AI to increase throughput, not to remove engineering discipline. The repo should make the correct implementation path obvious enough that an agent cannot casually rewrite architecture.

Tool roles

ToolBest use in this projectAvoid
ClaudeArchitecture critique, long-context refactors, schema reasoning, test-case generationLetting it redesign the whole system inside one implementation prompt
CodexScoped repository tasks, migrations, connectors, tests, debugging, implementation from written specsGiving vague “build the whole feature” instructions with no acceptance criteria
CursorFast local iteration, targeted multi-file edits, navigation, incremental refactorsAccepting broad generated diffs without reviewing boundaries and migrations

Required agent workflow

  1. Create or select one issue/story with explicit acceptance criteria.
  2. Ask the agent to inspect existing contracts before writing code.
  3. Require a short implementation plan for multi-file work.
  4. Implement the smallest vertical slice.
  5. Run typecheck, lint, unit tests, and relevant integration tests.
  6. Review the diff manually before accepting generated changes.
  7. Commit only after verifying database, connector, and API contracts remain intact.

Prompt template for implementation tasks

Goal:
Implement TRD requirement TR-XXX.

Relevant contracts:
- packages/schemas/...
- packages/domain/...
- docs/connector-contracts/...

Constraints:
- Do not change unrelated architecture.
- Do not add dependencies unless necessary.
- Preserve evidence provenance.
- All external/AI output must pass Zod validation.
- Add or update tests.

Acceptance criteria:
1. ...
2. ...
3. ...

Before editing:
Inspect the relevant files and give a short implementation plan.

Before completion:
Run typecheck, lint, and relevant tests.
Report files changed, tests run, and any unresolved risk.

Vibe-coding guardrails

  • No agent-generated database schema change without a migration and rollback/compatibility review.
  • No prompt strings scattered throughout the codebase; store prompt templates/version metadata centrally.
  • No direct vendor SDK usage outside connector/provider packages.
  • No generated “helper abstraction” unless it removes real duplication or enforces a domain boundary.
  • No merging code that passes typecheck but lacks behavior tests for extraction or signal logic.
  • Prefer boring, explicit code over clever framework tricks. This matters even more when agents maintain the repo.
