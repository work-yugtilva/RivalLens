3. Evidence & Versioning Model

snapshots = what the collector saw
observations = deterministic/validated facts extracted from a snapshot
signals = interpretation supported by observations
recommendations = action derived from one or more signals
reports = versioned presentation of current signals/recommendations
  • Snapshots and observations are append-only for V1. Corrections create new records rather than rewriting history.
  • Signals can change lifecycle state: active, weakened, resolved, dismissed.
  • Every AI-derived object stores model_provider, model_name, prompt_version, and analysis_version.
  • Use JSONB for variable connector payloads, but promote frequently queried fields into typed columns.

6. RLS & Authorization

Every table reachable through the Supabase Data API must have Row Level Security enabled and explicit grants/policies. RLS is not a substitute for correct grants.

Tenant rule

Access is granted when the authenticated user is a member of the organization that owns the brand ultimately associated with the row. Avoid duplicating user_id across every table solely for RLS convenience.

organization_members
  organization_id
  user_id
  role

brands.organization_id
competitors.brand_id -> brands.organization_id
...

Policy pattern

  • Use TO authenticated plus a membership predicate; never rely on the authenticated role alone.
  • UPDATE policies require both USING and WITH CHECK.
  • Views exposed through the API should use security_invoker = true where supported.
  • Never use user-editable metadata for authorization.
  • Service-role/secret credentials remain server-only and are never exposed to the browser.

7. Indexes & Constraints

UNIQUE organization_members(organization_id, user_id)
UNIQUE competitors(brand_id, domain)
UNIQUE sources(subject_id, connector_type, canonical_url)
UNIQUE social_posts(social_account_id, external_post_id)
UNIQUE jobs(idempotency_key)

INDEX snapshots(source_id, captured_at DESC)
INDEX observations(subject_id, fact_type, created_at DESC)
INDEX signals(brand_id, status, confidence DESC)
INDEX social_metric_snapshots(post_id, observed_at DESC)
INDEX product_snapshots(product_id, captured_at DESC)
INDEX connector_runs(source_id, started_at DESC)

Use partial indexes for active signals and active competitors if the working set becomes large. Add pgvector indexes only after real similarity workloads exist; do not pre-optimize the MVP.

8. Storage Layout

evidence/
  {organization_id}/
    {subject_id}/
      web/{source_id}/{snapshot_id}.html.gz
      screenshots/{snapshot_id}.webp
      social/{post_id}/...
      ads/{ad_id}/...
      reports/{report_id}.json
  • Bucket is private by default; access is via signed URLs or server-mediated retrieval.
  • Store hashes to deduplicate identical screenshots/creatives.
  • Define retention rules for raw HTML and media independently.
  • Database backups do not automatically represent object-storage backup strategy; treat them separately.

9. Migration & Schema Change Rules

  1. Create version-controlled migrations through the approved Supabase/Drizzle workflow.
  2. All schema changes include corresponding RLS/grant changes in the same review.
  3. Run database advisor/security checks before merging production migrations.
  4. Write RLS tests for allow and deny paths for organization isolation.
  5. Prefer additive/backward-compatible migrations; remove columns only after application code no longer reads them.
  6. AI agents may draft SQL, but schema ownership, constraints, indexes, and RLS must receive manual review.
